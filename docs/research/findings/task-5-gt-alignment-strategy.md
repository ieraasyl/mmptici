### C.8 How to exploit the template structure

**Per-family labeling strategy.** Label one chat per (family x archetype) cell first, not 20 random chats. A good 20-chat labeling set that covers every archetype: ru-001, ru-002, ru-003, ru-005, ru-009, ru-012, ru-014, ru-016, ru-018, ru-022, ru-023, ru-025, ru-026, ru-028, ru-029, kz-005, kz-008, kz-013, en-006, en-014. Hold out mirrors of the same archetypes for testing (for example tune on ru-007, test on en-007; tune on ru-014, test on kz-008; tune on ru-023, test on en-013), so a passing held-out score shows the prompt generalizes across languages instead of memorizing one chat. The 23 clean controls need only a spot check of 3 to 4 (one per language) to confirm no false alarms.

**Rules worth hard-coding** (cheap, deterministic, aligned with the planted markers) [inference]:

1. c07 = N/A when the last event is a connection-lost or client-left system event after the client's last turn.
2. c07 = No when the last event is "operator closed the chat" with no operator farewell before it.
3. c04 = N/A only when the client left before any request (client-left event and no request in client turns after escalation; the request at turn 1 counts as a request, so in ru-025 the "request" is just "talk to a human").
4. c03: locate the verification system event; if an account-specific operator statement precedes it, or exists with no event, propose No; if no account-specific statement or action exists, propose N/A. Let the model confirm.
5. c01: the first operator turn must contain a greeting word in the chat language and a self-introduction; ru-014 "Привет, где именно ищете?" and kz-008 "Сәлем." fail on the introduction.
6. c08: keyword prefilter for card transfers, personal numbers, "за плату", "ақылы", "I charge", plus insults; any hit forces the dedicated c08 call.

These rules are proposals to the LLM, not overrides, so that the replaced criterion at the organizers' check still runs through the general path.

**Synthetic generation of extra labeled chats.** The skeleton (C.1) is regular enough to generate new chats with labels by construction: take a family, pick an archetype, write the operator turns that realize it, and the label follows from the archetype. Value: tests that the evaluator catches each archetype in each language; gives few-shot material that is not in the DEV evaluation split. Risks: (1) labels by construction encode our reading of the ambiguous cases (C.6), so the synthetic set will agree with our prompt and tell us nothing about the organizers' reading; (2) if the same LLM writes chats and judges them, the defects will be phrased the way that LLM recognizes, which inflates measured agreement; (3) generation takes hours that the labeling of real DEV chats would use better. Recommendation [inference]: generate at most 10 to 15 chats, only for archetypes with one DEV example (announced wait, client-left, insult, verification declined), write them by hand or with a different model family, and never count them in the agreement number we report.

**What to expect in the control set** [inference]: same skeleton, same system-event strings, same three languages. Voice calls are possible because the DEV API returns them; they do not follow the skeleton, so rules 1 to 3 must fail safe (no matching event means the rules propose nothing). If the control set is hand-picked, the most likely archetypes are those CASE_CONTEXT lists as planted (unanswered question, paid offer, insult, client left, cut-off, announced wait, late question, unverified action, verified by event): one or two of each.

### D.1 Estimating the human-human ceiling with 2 raters on 10 dialogs

Procedure: both raters label the same 10 dialogs independently, with the checklist text only, without discussing; then compute per-criterion raw agreement over 10, pooled agreement over 80 cells, kappa for c02/c03/c07 (three-class) only if both raters used at least two classes, total-score absolute difference per dialog, and the list of disagreeing cells.

How precise it is [computed in `ss.py`]: pooled agreement of 68/80 = 0.85 has a Wilson 95% interval of 0.756 to 0.912; 64/80 = 0.80 gives 0.70 to 0.873. Cells within one dialog are correlated, so the effective sample is smaller: with intra-dialog correlation 0.1, 0.2, 0.3 the design effect is 1.7, 2.4, 3.1 and the 80 cells are worth about 47, 33, 26 independent cells. A single criterion over 10 dialogs (9/10) has an interval of 0.596 to 0.982. Conclusion: the 10-dialog ceiling tells you which criteria are ambiguous (any criterion where the raters disagree on 2 or more dialogs), not a precise number. Use the disagreement list as input to step 1 of the playbook.

### D.2 How many labels to detect a 10-point agreement difference between two prompts

Paired design (both prompts on the same items), McNemar test, Connor (1987) formula as given at https://metricgate.com/docs/sample-size-mcnemar-paired:

n = (z_{1-α/2} * sqrt(p_d) + z_{1-β} * sqrt(p_d - δ²))² / δ², with δ = p21 - p12 = 0.10, α = 0.05 two-sided (z = 1.96), power 0.80 (z = 0.8416), p_d = p12 + p21 the share of items where the two prompts disagree.

| p12 (B worse) | p21 (B better) | p_d  | Criterion decisions needed | Dialogs at 8 cells each | Dialogs with design effect 1.5 |
| ------------- | -------------- | ---- | -------------------------- | ----------------------- | ------------------------------ |
| 0.025         | 0.125          | 0.15 | 116                        | 15                      | 22                             |
| 0.05          | 0.15           | 0.20 | 155                        | 20                      | 30                             |
| 0.075         | 0.175          | 0.25 | 194                        | 25                      | 37                             |
| 0.10          | 0.20           | 0.30 | 234                        | 30                      | 44                             |

All counts are rounded up to the next whole number. For comparison, an unpaired test of 0.75 vs 0.85 needs about 250 items per arm. Two practical consequences [inference]: (1) a 10-point gain on pooled agreement is large (on DEV most cells are easy), so real prompt edits will show 1 to 3 points pooled and must be judged per criterion on the cells they target; (2) with 14 tuning dialogs (112 cells) only an edit that fixes many cells and breaks almost none is detectable; in the extreme p12 = 0, an exact sign test needs 6 of 6 discordant cells in the same direction for p < 0.05 two-sided (0.5^6 x 2 = 0.031). So read discordant cells one by one, accept an edit when it fixes the targeted cells and breaks none on the held-out mirrors.

### D.3 What a DEV-based agreement number does not tell you

DEV labels are ours. If our reading of C.6 #1 is wrong, our DEV agreement can be 95% while the control agreement on c07 is near 30%. Report DEV agreement as "agreement with our labeling guide", and keep the guide's decisions for the C.6 cases visible in the UI as configurable rules.

### D.4 When an organizer answer changes a rule late

1. Write the answer into the criterion text in the checklist config (new revision), not into code; the organizers' replace-a-criterion check will exercise the same path.
2. Relabel only the affected cells in our labeled set (for the closing rule: the c07 column of the labeled chats; a 10-minute job), keep the old labels as a revision for comparison.
3. Re-run the evaluator on the labeled set (about 60 calls, under a minute on Cerebras per the team's measurement) and compare the per-criterion confusion tables before and after; accept if the changed criterion improves and the others do not move.
4. If the answer arrives after the control set is released, re-run the control set with the new revision and keep both runs; the appeal/reviewer workflow already stores original and final values, which is the honest way to show a rule change in the demo.
